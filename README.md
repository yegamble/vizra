# Vizra build kit
## Evidence-led strategy and 16 reusable prompts
Prepared 15 September 2026 for Yosef's Vizra project.

This kit contains proposed repository instructions, product/architecture/design guidance, a seed feature catalog, release criteria, 16 prompts, and example tracking records. It contains no Vizra application code, implemented CI, completed design screens, executed application tests, or certified feature-parity audit. Example manifests deliberately remain unverified. No GitHub repository was created or modified in preparing this kit.

## Start
Create or choose the Vizra repository, preferably one monorepo. Copy the kit contents into its root, reconciling rather than overwriting any existing instructions. The .github templates and CLAUDE.md/AGENTS.md belong at repository root; prompts and docs are read on demand. Files named .example.json are examples, not completed live ledgers.

Start Claude Code or Codex in that repository and send:

```
Read AGENTS.md and README.md. Execute prompts/00-scope-and-parity.md.
Use the supplied charter, architecture proposal, and source register.
Create the actual product baseline and atomic feature/control ledgers.
Do not write application code or claim parity completion in this run.
Propose the architecture decisions and smallest first runnable slice.
```

Review material scope/architecture decisions once, then use Prompt 01 for the executable foundation. In parallel, use Prompt 02 for the first workflow's design, not an entire speculative application. Use Prompt 03 to prove the first real end-to-end gallery path, including privacy, restart, and early restore rehearsal.

## Daily use
Use Prompt 04 for one acceptance item at a time. Add only the relevant specialist prompt, rather than repasting the full project description. Use Prompt 15 to resume from a saved plan. Prefer finishing an in-progress slice over opening new partially complete work.

```
Read AGENTS.md. Execute prompts/04-deliver-one-feature.md for the next
ready acceptance item in the current milestone. Load only its relevant
specialist prompt and approved design. Implement and verify the entire
slice, then report evidence and remaining gates. Do not merge or deploy.
```

A separate session uses Prompt 13 for independent verification. UI changes also use Prompt 12. Only after the chosen release profile is complete does Prompt 14 run the exact-release rehearsal.

## Recommended order
| Stage | Prompts | Required exit |
|---|---|---|
| Scope and contracts | 00 | Atomic baseline and explicit core/full claims; unresolved parity visible. |
| Architecture and foundation | 01 | Real build/Compose/CI/browser environment and early clean-target path. |
| First workflow design | 02 | Accepted tokens/components/screens/states and control mapping. |
| First usable gallery | 03, 11, 12, 13 | Secure install → real upload/view/album/privacy → restart/restore. |
| Complete media/community | 04 with 05/06/11 | Fully implemented feature slices, real provider paths, growing recovery coverage. |
| Search and analytics | 04 with 07 | Useful permission-safe search; analytics optional and fault-tolerant. |
| Network integrations | 04 with 08/09/10 | Native protocol outcomes and real peer/provider evidence. |
| Parity and release closure | 06, 11, 12, 13, 14 | All full-profile obligations verified; exact release rehearsed. |

Chronology is dependency-driven, not a reason to leave security or backups until the end. Basic search and local statistics can ship before advanced analytics. A simple core release can be useful but is not the completed full-feature request.

## The main lesson
Make 'done' an observable result enforced by tests and review, not an adjective the agent chooses. A required missing/skipped/unexecuted test blocks the claim it was supposed to establish. A good prompt reduces ambiguity; it cannot replace a real test environment or manufacture provider credentials, infrastructure, human review, or a working application.

## Running an instance: diagnosing this release

**IGNORE THE `healthy` COLUMN.** `docker compose ps` reports api and worker
healthy whenever the binary can execute — their probe is `vizra version`, which
never opens a socket and never touches PostgreSQL. `docker compose up -d --wait`
returns success against a wedged api for the same reason. frontend's probe is
liveness-only too: it says the process renders, not that vizra-core is reachable.

Ask the API itself instead. The production overlay publishes it on loopback for
exactly this:

The ports are the defaults of `VIZRA_HTTP_PORT` and `VIZRA_FRONTEND_PORT`; if
you changed either in your env file, use yours.

```
curl -fsS http://127.0.0.1:8080/healthz              # :8080 = VIZRA_HTTP_PORT; liveness
curl -sS http://127.0.0.1:8080/readyz; echo          # NO -f: /readyz answers 200 "degraded"
                                                     # for cache down, search misconfigured or
                                                     # a queue backlog, and -f would exit 0 on
                                                     # it. Read the JSON: it names the component.
                                                     # 503 means PostgreSQL is unreachable.
curl -fsS http://127.0.0.1:3000/health               # :3000 = VIZRA_FRONTEND_PORT; process only
```

Real probes land with `vizra healthcheck` (vizra-core, queue 2h). **This section
is deleted in the same PR that empties `known_false_probes` in
`scripts/compose-shapes.json`**, and that is enforced rather than remembered:
`scripts/check-compose-topology.py` fails with `known-false-undisclosed` when
the list is non-empty and this disclosure is missing from either file that must
carry it, and with `known-false-stale-disclosure` when the list is empty and
either file still carries it.
