## Acceptance
1. `contracts/vizra-core/api/openapi.yaml` is byte-identical to
   `yegamble/vizra-core@415a6d19cfc0acedd8ad84c1857c95db0ed63627:api/openapi.yaml`, shown by git blob id.
2. `contracts/manifest.json` records `source_repo`, `source_ref: main`, the 40-hex `source_commit`,
   `sha256` and `bytes` of the vendored file.
3. `lib/api/generated.ts` is regenerated by the script, never hand-edited; spec + manifest + client
   committed together; `npm run check:contract` green.
4. The spec diff `b0dbeb6 → 415a6d1` is reported in structural terms.
5. Demonstrated red/green: (a) hand-edited generated client fails the drift check;
   (b) an in-place edit of the vendored spec fails on sha256; (c) the non-local `$ref` guard fires;
   (d) **new** — a manifest whose `source_commit` is not 40-hex, whose `source_ref` is not `main`,
   or whose `bytes`/`sha256` do not match the vendored file, fails `check:contract`.
6. AGENTS.md states that STALENESS (core moving on past the vendored commit) still cannot be
   detected from this repository's CI without a read token for private `vizra-core` — an open owner item.

**Non-goals.** Harness hardening, artifact privacy, tokens, shell, pages, any change in `vizra-core`.
The chair has ruled that core will rename `VIZRA_SEARCH_HMAC_KEY` to the contract's `SEARCH_HMAC_KEY`
in a later core slice; that will need a further re-vendor and is deliberately not pre-empted here.

- `scripts/vendor-contract.mjs`: read the spec from a **git revision** (`--ref`, default `main`)

  `source_ref`, the resolved 40-hex `source_commit`, the git `source_blob` id, `sha256` and `bytes`.
- `scripts/check-manifest.mjs` (new) + `scripts/check-manifest.test.mjs`: the manifest self-check
  (verifier Finding 3 from PR #1), called from `scripts/check-contract.mjs`.
- `contracts/manifest.json`: re-pointed provenance, `$schema_version` 2.
- `AGENTS.md`: the new command form, the manifest check, and the staleness gap as an owner item.
- `.github/workflows/contract-ci.yml`: the manifest check as a named step of its own, and the
  header comment corrected to say what the lane does and does not prove. No other workflow touched.
- No change to `lib/`, `app/`, `e2e/`, `contracts/vizra-core/api/openapi.yaml`,
  `.github/required-checks.txt` or `e2e/harness/required-projects.json`.
