## Round A — vizra-infrastructure

Q-001 MODIFY — Vidra's real operator tax: third image tag in the release triple, a second migrations table, a search_models volume, and "SEARCH_SERVICE_URL … or the search integration silently degrades to local SQL" (docker-compose.prod.yml:15-16). REPLACEMENT: create the repo at M0 with the HMAC contract but carry no search service, secret, volume or probe in the topology until the service answers queries; SEARCH_MODE=off default; a configured-but-unreachable search is a doctor/readyz-degraded failure still served from SQL — logged and reported, never silent.
Q-002 MODIFY — consumed as a version-pinned package or vendored asset, never fetched from a branch during an image build (bundle must be byte-identical).
Q-003 ACCEPT (ops-neutral, rider: /version and image labels expose resolved module versions). DEPENDS ON: v5 GA with a security-patch track.
Q-004 MODIFY — Valkey 8.x managed unconditionally; EXTERNAL any RESP-compatible ≥ 7.0; compose sets maxmemory and allkeys-lru with a comment; backup never claims the cache; doctor prints flavour/version. DEPENDS ON: go-redis speaks to Valkey unmodified.
Q-017 MODIFY — Vidra enforces the floor in four places and fails closed on an unparseable string, but the prod overlay's `!reset []` is the only barrier. REPLACEMENT: floor asserted in CI on the rendered model and refused at runtime by install/deploy/rollback/restore/doctor; base compose publishes nothing; dev mappings in the override bound to 127.0.0.1.
Q-027 MODIFY — Vidra ships amd64-only images but cross-builds the CLI for four platforms. REPLACEMENT: images and acceptance amd64-only; CLI for linux/darwin × amd64/arm64 from M0; install.sh/doctor die with a named message on non-amd64; Apple-Silicon developers use the build-from-checkout chain.
Q-028 MODIFY — Vidra's floor is 4 vCPU/8 GB and "Do not use a 2 GB droplet". REPLACEMENT: 2 vCPU/4 GB only with pulled images, a 2–4 GB swapfile, worker concurrency 1, capped libvips cache, maxmemory; replace the 30 s budget with p95 < 8 s per derivative set for a 12 MP JPEG plus a burst budget (100 uploads drain in 10 min) and an oldest-pending-job-age metric; fixture declares bytes and megapixels; RPO covers originals; RTO 2 h measured for the actual byte volume and backup location — as written, unachievable for 40 GB off-site.
Q-032 MODIFY — add a read-token CI job comparing the live ruleset to a checked-in expected-protection file; until confirmed, no VERIFIED on CI evidence alone; the owner is the admin — a Prompt 01 owner action.
Q-034 MODIFY — base image pinned by digest, libvips version-pinned or built from a checksummed tarball, libvips layer below the Go layer; HEIC only after a licence review of libheif/libde265/x265, config-gated OFF; the image reports its decodable formats; the API rejects unsupported formats at upload time.
Findings: BLOCKERS F1 (RTO 2 h arithmetically unreachable for the declared fixture without locality), F2 (silent search degradation contradicts the charter). REQUIRED F3 (base publishes nothing), F4 (stuck-processing metric), F5 (refuse unsupported formats at the API), F6 (reproducible image builds). SHOULD F7 (refuse partial release triples), F8 (sizing table). EXPERIMENT F9 (measure search container cost on the reference host). NOT WORTH DOING: multi-arch release images at M0; a HEIC-enabled image variant; parsing `docker compose version` as the sole barrier; backing up the cache; a vizra-branding runtime artifact.
Position: two M0 decisions let an operator run a service that quietly does nothing and let a stale Compose quietly publish PostgreSQL; fix both by removing the dangerous default. Valkey should be decided, not conditional; amd64-only is right for images and wrong for the CLI; libvips is right and currently unreproducible; branch protection is an owner task with a drift check.

## Round B — vizra-architect (reply to the devil's advocate)

RETRACTED: "Create vizra-search in M0 as contract + migrations" — checked the mechanism: vidra/deploy/lib.sh:283 `release_mapping_check ROOT MODE CORE USER SEARCH` has fixed 5-arg arity, rollback.sh:75 fans a bare tag into all three, pin-release.sh:102 loops the three keys, `require_embedded_migrate_tag VIDRA_SEARCH_TAG` appears in deploy/rollback/restore. Adding a third component at M3 changes that arity, the releases/<tag>.json schema and the env template — but the deployment tree is pinned at the tag, so a pre-M3 release rolls back with its own two-component tree; the boundary is self-consistent. Cost at M3: one schema_version bump plus ~5 script sites. Cheaper than seven idle lanes and an empty image tagged at every release from M0. No repo, no image, no VIZRA_SEARCH_TAG until VZ-SEARCH-001 lands.
HELD: the Q-001 contract freeze — internal/search with sql and remote, schema `search` reserved (one DSN, one pg_dump). HELD: the Q-001 contradiction finding (VZ-SEARCH-004 core profile; META_REPO "always" plus mandatory triple).
REVISED: Q-008 — site_id key → database-per-tenant, no tenant column, no per-tenant schema. The default-deny argument decides it: a missed WHERE site_id leaks; a separate DSN cannot; VZ-TENANT-001 already names "database isolation". Could not produce the falsifier: every tenant-scoped obligation is single-tenant per query.
HELD: something must be frozen at M0 — no package-level DB handle (pool from request/job context); Redis and storage key prefixes from context; worker loops a tenant registry; migrator applies to N databases with a per-database ledger and explicit partial-failure state; backup.sh iterates tenants. One unpriced cost: vizra-search takes a single DATABASE_URL, so database-per-tenant means N search DSNs or one search instance per tenant.

## Round B — vizra-devils-advocate (reply to architect and infrastructure)

REVISED: Q-001 MODIFY → ACCEPT with one condition. Falsifier satisfied: vidra/releases/v0.6.4.json is schema_version 1 with a fixed components{core,user,search} map and a top-level search_schema_version; deploy.sh:502,536,554 and rollback.sh:67-79,154,255,310 hard-wire three tags, `for repo in vidra-core vidra-search vidra-user`, and per-component MIN_EMBEDDED_MIGRATE_TAG gates. A two-then-three switch is a record-format bump plus an absent-component path in deploy, rollback, restore, bundle and setup — more than seven idle lanes. Infrastructure's SEARCH_MODE=off plus degraded readiness removes the idle-container cost. CONDITION: the M0 search image must be a real service answering /healthz and /internal/v1/search with an explicit "not indexed" response that core treats as fallback — not a placeholder — and search_schema_version must not report a number for an empty ledger.
HELD: "M2" is wrong regardless of repo timing.
RETRACTED: "database-per-tenant needs zero changes" — zero query changes; the same cross-cutting plumbing as site_id (cache keys, storage prefix, job payload, federation actor).
HELD: database-per-tenant, because that plumbing freeze is required anyway for external PostgreSQL/Redis and multi-location storage, whereas site_id additionally lands in every table, composite unique constraint and sqlc query from M0.
REVISED: M0 checklist — (1) no package-global pool/Redis/storage/search client; one context resolver with a single default implementation, enforced in make ci; (2) hostname→tenant resolution in exactly one middleware; (3) storage key prefix from the resolver, default `default`; (4) Redis key namespace from the resolver; (5) one tenant field on job rows only, so leasing is worker fan-out; (6) migrator takes a DSN and exits per DSN, both ledgers; (7) federation actor from request hostname, not a global base-URL constant.

Q-008: database-per-tenant with the M0 plumbing checklist; item (5) of the devil's advocate's list (a tenant field on job rows) was not adopted because jobs live in each tenant database.
