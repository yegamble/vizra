## VZ-FOUND-003

### What the "compatibility window" rule actually is

There is no window. `vizra-core/scripts/migrate-lint.sh:87-107` (rule 4) greps
every `*.up.sql`, old or new, line by line and case-insensitively, for this
pattern (`migrate-lint.sh:92`):

```
DROP\s+(TABLE|COLUMN|CONSTRAINT|INDEX|TYPE|SCHEMA|VIEW|SEQUENCE)
| ALTER\s+TABLE\s+[^;]*RENAME
| ALTER\s+TABLE\s+[^;]*ALTER\s+COLUMN\s+[^;]*TYPE
| TRUNCATE
```

A matching line fails unless the line is a `--` comment or the line immediately
above it is `-- allow-destructive: <any non-empty text>` (`migrate-lint.sh:98-103`).
Nothing in the script reads a release tag, a migration age, a version range or
a rollback floor, so "inside the compatibility window" in the ledger outcome and
in the script's own header (`migrate-lint.sh:11,88`) has no mechanical meaning.
ADR-002 still marks the rollback floor `[to confirm in M0]`
(`docs/adr/ADR-002-repository-process-release-configuration-ownership.md:74`).
In effect the rule is: "always, unless a one-line comment says otherwise".

What the pattern does and does not catch, each shown on a new migration `0006`
with the manifest regenerated:

| Statement | Transcript | `make migrate-lint` |
|---|---|---|
| `ALTER TABLE sites DROP COLUMN handle;` | `F003-M1` | exit 2 (red) |
| `ALTER TABLE sites DROP handle;` (the `COLUMN` keyword is optional in PostgreSQL) | `F003-M2` | **exit 0** |
| `DROP` and `COLUMN` on separate lines | `F003-M3` | **exit 0** |
| `DROP COLUMN` under `-- allow-destructive: x` | `F003-M4` | exit 0 (the designed exemption; nothing checks the reason or who approved it) |
| `DROP FUNCTION … CASCADE`, `DELETE FROM`, `DROP TRIGGER` | `F003-M5` | exit 0 (not in the pattern) |

The lint has its own guard: removing `COLUMN` from the pattern turns
`TestMigrateLintFixtures/drop-column` red (`scripts/scripts_test.go:66`, `F003-M8`).

- `VIZRA_OWNER_CLAIM_TTL` (read at `internal/config/config.go:260`)

`env/registry/*.json` (`F006-KEYS-template`). An operator of the compose
deployment cannot set either; the containers get the built-in defaults (`off`
and `1h`).

`.github/workflows/validate.yml:297`), because `scripts/check-config-coverage.py`
does not read core. It reads `env/registry/core.json`, a snapshot taken at core
`4a80a1e` with 22 keys, before the owner-claim slice added two. The check that
compares snapshot with source is `--drift`; it is red here (`F006-META-DRIFT`,
exit 1, naming both keys) and by its own documentation cannot run in meta CI
(`scripts/check-config-coverage.py:41-46`). The same drift run reports 36 names
for vizra-search; most are noise from its coarse scan of `AGENTS.md` and the
Dockerfile, but `VIZRA_MODE` is real: vizra-search reads it
(`vizra-search/internal/config/config.go:125`) and its snapshot does not list
it. That one is outside these three ids and I did not follow it further.
